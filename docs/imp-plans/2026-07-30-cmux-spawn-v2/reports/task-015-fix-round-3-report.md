**Implementation Summary:**

This is fix round 3 for Task 15, closing the two Critical findings from `docs/imp-plans/2026-07-30-cmux-spawn-v2/reports/task-015-quality-review.md` — the first quality review for this task, run against the round-2 fix (`710c40f`, `85e4190`) after its spec re-review passed.

**C1 — realpath fix has zero coverage.** The round-2 fix switched `os.path.abspath` to `os.path.realpath` on both sides of the `relpath` call in the `elif args.reports_dir:` branch, to handle macOS's `/tmp` → `/private/tmp` symlink resolution. The quality reviewer measured that pytest's `tmp_path` fixture is *already* realpath-canonicalized on this machine (`os.path.realpath(tmp_path) == tmp_path`), unlike a raw `tempfile.mkdtemp()` call (which returns the unresolved `/var/folders/...` form on macOS, `realpath` resolving it to `/private/var/folders/...`). Reverting `realpath` to `abspath` in either spot therefore left the existing 47-test file fully green.

I added `TestGitRealityUnresolvedTempRepoPath`, building its workspace under a directly-created `_init_temp_git_repo()` repo (the same helper `TestGitRealityCheck` already uses, for exactly this reason) instead of pytest's `tmp_path`. The key finding while writing this test: a **source-commit-fails** test (mirroring the existing caller-derivation pattern) does **not** discriminate the mutation — I verified this empirically first and it surprised me (see Self-Review). Both shipped code and an `abspath` mutant correctly FAIL a real source-file commit in the unresolved-path scenario, because under the mutant the malformed relpath candidate (no common prefix between `/var/folders/...` and `/private/var/folders/...`, so it comes out `..`-prefixed) gets rejected by the new C2 `_sanitize_exclude_dir()` and Check 9 falls back to running *unnarrowed* — which still finds the source commit. The test that actually discriminates is a **bookkeeping-only-commit-passes** test: under the mutant, the same unnarrowed fallback also flags the bookkeeping commit as a violation (FAIL instead of the expected PASS), which is the real, security-relevant regression (a legitimate SDD hop-bookkeeping commit on an unresolved-tmp-path repo would wrongly block completion). `test_bookkeeping_commit_passes_unresolved_repo_path` is the mutation killer; `test_source_commit_fails_unresolved_repo_path` is kept as a secondary sanity check but documented as non-discriminating in its own docstring.

**C2 — `exclude_dir == "."` fail-open.** When `reports_dir`'s parent (the feature dir) IS the git root itself — legal since `--reports-dir` is free-form and unvalidated — `os.path.relpath(feature_dir, git_root)` yields `"."`, and `git log -- . :(exclude).` excludes the entire repository, silently certifying any commit (including a real source-file modification) as clean. Added `_sanitize_exclude_dir(candidate)`: returns `None` (treated identically to "no exclude_dir configured") when the candidate normalizes to `"."`, `""`, or starts with `".."` (the latter covers a candidate that resolves outside `git_root` entirely — unreachable/malformed as an in-repo pathspec). Both the `elif args.reports_dir:` and manifest branches now sanitize their raw candidate and track `exclude_dir_narrowing_failed` (true only when a candidate *was* derived but got rejected — distinct from "no feature_dir key at all"), which appends a note to the check detail so a controller reading pre-completion output can tell Check 9 ran unnarrowed rather than assuming full protection.

Added `TestGitRealityExcludeDirNormalizesToRoot` with a new `_build_verification_workspace_at_root()` helper (lays `reports/`, `plan.md`, `deviations.md` directly at `repo_root` instead of nested under `docs/imp-plans/feat/`) and two tests — reports_dir mode and manifest mode — both committing a real `src/feature.py` source file and asserting Check 9 still FAILs, plus asserting the narrowing-failed note text is present in the detail.

**I1 (deferred).** Per the task brief, I1 was explicitly optional and only worth folding in if it fell out naturally from the C2 work. It does not: `_check_verification_git_reality` currently returns a plain `list` of findings, and the caller (`run_pre_completion`) builds its detail string by iterating that list assuming every element is a file-modification finding with `task`/`start`/`end`/`commits` keys. Distinguishing "git log errored" from "found nothing" requires either a second return value (tuple) or a differently-shaped list element, either way changing the return contract and the caller's consuming loop — outside this round's C1/C2-only scope. Documented as a deferral rather than silently dropped.
