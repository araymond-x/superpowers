# cmux Auto-Spawn Skill-Awareness Audit

Date: 2026-08-04
Feature: `docs/imp-plans/2026-08-04-cmux-spawn-v2-remediation/` (Task 10, Module 3)

## Question

The context-pressure gate (`sdd-pre-dispatch-hook.sh`, registered globally as a `PreToolUse` → `Agent` matcher hook — confirmed at `~/.claude/settings.json`) and the auto-spawn mechanism it triggers (`spawn-handoff-session.sh`) are wired into the SDD skill family. This audit asks: which skills' execution flows can actually reach that gate, and — for those that can — does the skill's text now carry awareness of auto-spawn as the default block-response? For skills that can't reach the gate, does the audit confirm no awareness is needed?

## Mechanism recap

`sdd-pre-dispatch-hook.sh` is registered on the `Agent` tool matcher in `~/.claude/settings.json` — not scoped to any one skill. It fires whenever **any** controller (regardless of which skill orchestrated it) dispatches a subagent via the `Agent` tool, provided a `.sdd-session.json` manifest is present (manifest mode, required since the 2026-05-29 SDD Hook Improvements). So "reaches the gate" reduces to: **does this skill's controller dispatch implementer subagents via the Agent tool, under a materialized SDD manifest?**

## Conclusion

Every skill whose controller can actually dispatch an implementer via the Agent tool under an SDD manifest — which today is only `subagent-driven-development` — carries auto-spawn awareness after this feature's Module 2/3 edits. `writing-plans` and `brainstorming` don't reach the gate themselves, but both now carry the `handoff_spawn` consent field/choice that flows into the manifest the gate reads, so the awareness is present exactly where it's load-bearing (the authoring step, not the dispatch step). `executing-plans` and `using-superpowers` correctly carry no awareness because neither ever performs an Agent-tool dispatch under an SDD manifest — `executing-plans` is architecturally the no-subagent fallback path (it says so in its own text), so the context-pressure gate is out of scope for it by design, not by oversight.

**Follow-up worth flagging (not a gap in this audit's scope, and not fixed here):** `executing-plans`' own preamble already tells the user subagent-driven-development is the better path when subagents are available — that sentence is the existing steering mechanism away from the no-gate path. This audit did not find a textual gap that needs its own pointer to auto-spawn (there is nothing in `executing-plans` for such a pointer to attach to, since it has no context-accumulation concept or handoff mechanism of its own — a long-running inline `executing-plans` session would still hit a context wall, but its *only* relief valve is the human/Claude-Code-level context management, not an SDD block/handoff). If a future BACKLOG item wants `executing-plans` sessions to also benefit from auto-spawn, that would be new functionality (giving `executing-plans` its own context-pressure detection and handoff path), not a documentation-awareness fix — recommend filing it as a distinct BACKLOG idea rather than folding it into this feature's discoverability sweep.
